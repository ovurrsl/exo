## What is good, and should be said out loud in the description

**It is opt-in, not opt-out.** `Args.telemetry` defaults to `False` and
`--telemetry` is what turns it on; without the flag `TelemetryService` is created
with `telemetry_disabled=True` and stays in dry-run. That is the single most
important property of a telemetry PR and the description does not lead with it.
Reviewers will assume the opposite unless told.

**The presign request carries no identity.** It posts only:

```python
json={"sha256": sha256, "size": len(data)}
```

No node id, no hostname, no user, no model. That is a genuinely careful design —
the server cannot correlate uploads to an installation from the metadata alone.

**The endpoint is overridable.** `EXO_TELEMETRY_API_URL` means a fleet operator
can point this at their own collector instead of `telemetry.exolabs.net`.

## The gap

`_submit_runner_stderr` reads the runner's stderr log with `path.read_bytes()`
and PUTs it verbatim. There is no redaction pass. Runner stderr is the raw stderr
of the inference subprocess, so in practice it can contain:

- absolute filesystem paths, which on a default install embed the user's home
  directory and therefore their username;
- model identifiers, which for a private or unreleased model card is itself
  sensitive;
- whatever appears in a Python traceback, which for an exception raised inside
  generation can include prompt text.

The third one is the sharp edge, and it interacts with #2290. loguru's
`diagnose=True` default writes the *values* of locals into tracebacks — I
confirmed separately that it calls `repr()` on locals referenced by the failing
line. If #2126 lands before #2290, a crash during generation can upload prompt
content to a remote endpoint. If #2290 lands first, that specific path is closed.
I would make #2290 a prerequisite of this PR, or land them together.

## Concrete suggestions

1. Add a redaction pass before upload — at minimum `$HOME` to `~`, and the
   models directory to a placeholder. Cheap, and it removes the username leak
   entirely.
2. Document in `--telemetry`'s help text *what* gets uploaded, not just that
   something does. "Uploads runner stderr logs on crash" is one clause and makes
   the consent meaningful.
3. Land #2290 first, or pull `diagnose=False` into this PR.
4. Consider a size cap. A runner that crash-loops with a verbose backend can
   produce a very large stderr file, and there is currently no ceiling on what
   gets PUT.

None of these are blockers for the architecture, which I think is sound. They are
about the contents of the payload rather than the mechanism that carries it.
