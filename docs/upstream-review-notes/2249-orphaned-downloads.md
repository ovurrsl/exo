## Re-sending in a loop is fine here

My first concern was that `_plan` runs every 10 seconds and will keep emitting
`NodeTimedOut` for the same node until the state converges. That turns out to be
the established behaviour of this loop already — the existing "time out dead
nodes" block immediately below does exactly the same thing, re-sending
`NodeTimedOut` on every pass until `last_seen` is pruned. So this PR is
consistent with its neighbour rather than introducing a new wart. Worth
mentioning in the description so a reviewer does not have to rediscover it.

## The naming concern

The new code reuses `NodeTimedOut` as a garbage-collection signal for a node that
did not time out — it vanished from the topology without the master ever
recording a timeout. Functionally that is fine, because `apply_node_timed_out`
prunes `downloads` first and the node is already absent from the topology, so the
event is idempotent. But it does write a "node timed out" entry into the global
event log for a node that never did, and anything that surfaces those events (the
dashboard, future telemetry, anyone debugging from a log) will read it as a real
timeout.

If the event log is meant to be a faithful history, a distinct event —
`NodeDownloadsOrphaned`, or reusing whatever removal event the topology path
already emits — would be more accurate. If the event log is purely a state
transition mechanism, reuse is the cheaper answer and this is a non-issue. That
is a maintainer call about what the event stream is *for*, which is why I am
raising it rather than asserting it.

## Minor

The new GC block is placed above the "kill broken instances" block, so on the
first pass after a node disappears the orphan event is queued and the instance
sweep still runs against the pre-event state. It converges on the next pass, so
this is cosmetic, but placing the GC after the instance sweep would make each
pass internally consistent.
