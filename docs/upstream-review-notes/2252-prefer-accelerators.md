## The part that needs a maintainer decision

`_cycle_accelerator_score` is inserted as the **first** element of the `max()`
sort key, i.e. above `_cycle_download_score`:

```python
key=lambda cycle: (
    _cycle_accelerator_score(cycle, node_backends, required_backends),
    _cycle_download_score(cycle, command.model_card.model_id, resolved_download_status),
    ...
)
```

That is not just "prefer accelerators", it is "prefer accelerators even over
already-downloaded weights". A cycle that has the model fully downloaded on a CPU
node now loses to a cycle with an accelerator and nothing downloaded, which
means a fresh multi-gigabyte download before the first token. For a small model
that is obviously the right trade; for a 100 GB model on a slow link it may not
be.

Swapping the two entries — download score first, accelerator score second —
would give "prefer accelerators among equally-ready cycles" instead, which is the
less surprising reading of the PR title. I do not know which the maintainers
want; I only want to flag that the ordering *is* the policy, and the PR reads as
though it were a bug fix rather than a policy choice.

## Two smaller notes

`_cycle_accelerator_score` returns an absolute count of accelerator-capable
nodes, so between two cycles it also weakly prefers the larger cycle: a 4-node
GPU cycle scores 4 and a 2-node GPU cycle scores 2, even when both can host the
model. If that is not intended, a boolean ("does this cycle have any
accelerator") or a fraction of the cycle would be more neutral.

The intersection with `required_backends` is the right guard — for a CPU-only
model card every cycle scores 0 and placement behaviour is unchanged, so the
blast radius is limited to genuinely heterogeneous clusters. Worth saying in the
description; it makes the change much easier to accept.
