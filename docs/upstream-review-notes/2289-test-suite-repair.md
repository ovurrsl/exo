## Why the `__init__.py` is the right fix, not a workaround

Under pytest's default `prepend` import mode the module name of a test file is
derived by walking up from the file while `__init__.py` files exist. Because
`src/exo/download/tests/__init__.py` exists but `src/exo/download/__init__.py`
does not, that walk stops at `src/exo/download/`, so those files get the module
names `tests.test_cancel_download` and friends — which collide with the
top-level `tests/` package.

I checked whether this is a one-off or a pattern. It is a one-off:

```
$ find src -type d -name tests | while read d; do p=$(dirname "$d"); \
    [ -f "$p/__init__.py" ] || echo "MISSING: $p/__init__.py"; done
MISSING: src/exo/download/__init__.py
```

`src/exo/download` is the only test-parent directory in the tree missing an
`__init__.py`. So the one-line addition restores the invariant every other
package already holds, rather than papering over a layout problem.

## One correction to the framing

The PR description reads as though CI is broken. It is not — `pipeline.yml`
runs pytest with `--import-mode=importlib`, which derives module names from the
file path and is therefore immune to this collision. What is broken is the
*locally documented* path: `uv run pytest` from the repository root, which is
what `AGENTS.md` and `CONTRIBUTING.md` tell a contributor to run. Saying that
explicitly would probably make the PR easier to accept, because it stops a
reviewer from going to check CI and concluding the premise is wrong.
