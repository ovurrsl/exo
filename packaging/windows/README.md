# Windows runtime and installer

The Windows build is isolated from the existing Mac spec, Swift app and workflows.
The Tauri desktop shell owns the node process at `runtime/exo.exe`, with its onedir
siblings kept intact. Python, MLX, CUDA 13 runtime libraries, NVRTC, CUDA/CCCL
headers, Exo resources, the dashboard, tokenizer metadata and dynamic model modules
are included. The end user needs an NVIDIA display driver compatible with CUDA 13;
neither Python, Visual Studio Build Tools nor the CUDA Toolkit is required.

## Build

Prepare the pinned Python 3.13 environment and build the reviewed Windows MLX patch
with `scripts/windows/mlx/build-mlx-wheel.ps1`. Install that exact candidate wheel
without resetting the environment. Its adjacent `.provenance.json` is required.
The source checkout pins the Windows dependency to a local wheel path because this
candidate has not been published. Stage the reviewed binary before syncing GPU
extras; the tracked provenance records its exact hash. CPU CI's `mlx-none` extra
does not require that file. The Mac git source and its locked version remain fixed.

```powershell
.\scripts\windows\prepare-runtime-wheel.ps1 -WheelPath C:\path\mlx-0.32.3.dev20261009+win.3-cp313-cp313-win_amd64.whl
uv sync --frozen --extra mlx-cuda13
.\scripts\windows\build-runtime.ps1 -MlxWheel C:\path\mlx-0.32.3.dev20261009+win.3-cp313-cp313-win_amd64.whl
.\scripts\windows\build-installer.ps1 -MlxWheel C:\path\mlx-0.32.3.dev20261009+win.3-cp313-cp313-win_amd64.whl -SkipRuntimeBuild
```

The commit and patch pin reproduce the source inputs. A compiler rebuild can have
different wheel bytes, so it is a new candidate: run the native/frozen gates and
explicitly update the reviewed provenance and lock before using it. The staging
script refuses a different hash and never substitutes an unpublished download URL.

`build-runtime.ps1` checks the source/patch/wheel identity, builds the dashboard and
onedir runtime, runs the frozen CUDA/CPU/spawn/>2GiB/ring failure gates, and writes
`dist/windows/exo/runtime-manifest.json`. `build-installer.ps1` stages the complete
runtime under `app/windows/src-tauri/resources/runtime/` and builds a per-user NSIS
installer. `prepare-webview2.ps1` downloads the pinned Microsoft fixed runtime,
verifies the CAB and executable hashes plus Microsoft's executable signature,
and compares every staged file. `-WebView2Archive` accepts a cached pinned CAB.
Tauri bundles and loads it at `resources/webview2`, independent of machine-wide
Evergreen registration; the installed app can start offline. Fixed WebView2
security patches require a reviewed pin update and a new Windows app release.
Model downloads still require network access
until the requested weights are cached.

The package entrypoint dispatches multiprocessing helpers before application
imports and supports `-c` for Exo's bounded CUDA health probes. The runtime DLL hook
preserves the NVIDIA package hierarchy and configures DLL directories before MLX
is imported. CPU-stream fusion is disabled by the Windows native patch, while
CUDA fusion uses bundled NVRTC and headers with a fresh cache.

## Required evidence before release

The JSON manifest contains the upstream MLX commit, patch/wheel hashes, installed
package versions, every frozen runtime file hash and the runtime gate report.
The schema 2 manifest covers DLLs, Python modules, CUDA headers, resources and
the dashboard. Installer staging validates the exact file set and every hash both
before copying and after copying, rejecting links/junctions and path escapes.
An older manifest must be regenerated by a validated runtime build. It marks
`release_ready: false` until physical cross-platform validation is recorded.
`windows-ci.yml` runs hosted CPU/unit/Rust/desktop checks; `windows-package.yml`
builds a candidate on an explicitly configured physical CUDA machine.

On a physical Mac and Windows node, run `check_mlx.py --worker ring --device gpu
--exo-hook` (the frozen Windows command starts with `exo.exe --runtime-check`) with
the same hostfile and respective rank. Then validate same-model PP and TP output,
cache-on/cache-off, topology changes and runner cancellation, followed by chat,
vision and supported image workflows through the installed app. Also test the
installer on a clean Windows system without a compiler, Python or Toolkit. Neither
loopback collectives nor packaging success establish this product parity.

Without `TAURI_SIGNING_PRIVATE_KEY`, the installer script builds an unsigned review
candidate and disables updater artifacts through a temporary Tauri configuration.
`-RequireSignedUpdater` requires both that release secret and the compiled
`EXO_WINDOWS_UPDATER_PUBLIC_KEY`. Updater
signing and publication are separate release operations. No private key is included
in this package or these scripts.
